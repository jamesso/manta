## Facts behind the plan

- Electron 45.2.0 (Chromium 156, Node 24.22) supports macOS 13+, Windows 10+, and 64-bit x64/arm64 only. Electron 45 has no 32-bit builds, so the `ia32` targets go. Electron 44 raised the macOS minimum to 13. Sources: [Electron 45 release](https://www.electronjs.org/blog/electron-45-0), [breaking changes](https://electronjs.org/docs/latest/breaking-changes), [rstudio#19063](https://github.com/rstudio/rstudio/issues/19063).
- Electron 1.8 has no arm64 build, so on Apple Silicon it runs only through Rosetta 2. The universal mac build in 011 removes that dependency.
- Package versions were checked on the npm registry on 2026-10-30/31. Each plan says to confirm the versions with `npm view <pkg> version` at execution time.

## Findings considered and rejected

- **Keep Electron 43 to support macOS 12:** rejected. Electron 43 stops getting security fixes when Electron 46 ships, so this only delays the migration.
- **Keep webpack (upgrade to webpack 5) instead of electron-vite:** rejected. It would need about 8 webpack and Babel plugins to replace react-hot-loader and Babel 6. electron-vite covers main, preload and renderer builds and Fast Refresh in one config.
- **Replace `moment` with date-fns or dayjs:** rejected for now. User settings store moment format tokens (for example `invoice.dateFormat = 'MM/DD/YYYY'`), so 006 upgrades moment to 2.31 instead.
- **Rewrite Redux code with Redux Toolkit:** rejected. It is not needed to run on current systems. `redux-actions` 3 still works with Redux 5.
- **Rewrite to TypeScript or function components:** out of scope. It adds no OS or dependency support.
- **Skip React 18.3 and go to 19 directly:** rejected. React 18.3 warns on every API that 19 removes, and it still runs the old libraries while they are replaced.

### Shared data decisions

- **Document types (022, 023):** all sales documents stay in the `invoices` database. The field `docType` is `'invoice' | 'estimate' | 'creditNote'`. A missing value means `'invoice'`. 022 makes the `getInvoices` selector return invoices only, and adds a second filter in the dashboard, CSV and client summaries.
- **Numbering:** one counter per type: `invoice.numbering` (015, `INV-`), `invoice.estimateNumbering` (022, `EST-`), `invoice.creditNoteNumbering` (023, `CN-`). Saving one type never moves another type's counter. Recurring drafts (024) get a number only when the user first saves them, so deleting an untouched generated draft does not consume a number. This does not guarantee gap-free numbering across crashes or deleted saved documents.
- **Payments (020):** a `payments` array on the invoice. Use the same currency rounding in payments, credit allocation, tax totals, dashboard, CSV and PDF output. Pass the full sales-document set to credit-aware calculations before filtering display lists. `getBalanceDue` = total − payments (− issued credit notes after 023). The stored statuses do not change. `partial` is a display status only. Old `paid` invoices with no `payments` field count as paid in full. Credit settlement must not be converted into synthetic cash receipts. Overpayment is refused.
- **Tax (021):** `invoice.taxRates` with UNCL5305 categories (S, Z, E, AE, K, G, O) and exemption reasons. Rows store a copy of the rate. Old documents keep the invoice-level `tax` object, and `getInvoiceTotals()` gives the same numbers as before for them (golden tests). Tax is rounded once per rate group (EN 16931 BR-CO-17). The seller tax IDs move to `profile.taxId`/`profile.vatId`. The fallback is `invoice.tax.tin`.
- **Items (019):** a new database `items`. Rows store `unitCode` (UN/ECE Rec 20, default `C62`) but no item id. Editing an item never changes saved invoices.
- **Recurring (024):** a new database `recurring`. Profile dates are local `YYYY-MM-DD` strings. Created drafts get a fixed `_id` `rec-<profileId>-<periodKey>`, so retries cannot create two live drafts for the same period. Keep tombstones or an equivalent completion record so deleting a generated draft does not make the runner create it again. The app checks at startup, every hour, and when the computer wakes up (`powerMonitor` `resume`). It never sends anything automatically.
- **E-invoice (025):** library `@e-invoice-eu/core` (WTFPL, compatible with GPL-3.0). Factur-X EN 16931 (CII) for the hybrid PDF and XRechnung as UBL. Shared pure code is in `helpers/einvoice/`. Step 0 tests whether Chromium `printToPDF` output can pass veraPDF as PDF/A-3. If it cannot, only 025a ships. Peppol is out of scope.
- **Email (026):** `mailto:` (it cannot attach files; RFC 6068) plus "show the PDF in its folder". On macOS, Electron `ShareMenu` adds "Share PDF…". The main process builds the `mailto:` URL itself and accepts no other scheme. The URL is limited to 1,800 characters. Optional fields `sentAt` and `remindedAt` record user confirmation only; opening a mail client is not proof of delivery.
